# TxtRPG — World Node Expansion & Depth Research

> **2026-10-17 | Research / Proposed.** 기술 조사 및 개발 후보 명세. **확정 Canon·게임 코드·기존 save 스키마 변경 없음.**
>
> **기준:** `feature/v2-core`, `AGENTS.md`, `docs/v2/DEVELOPMENT_RULES.md`, `docs/v2/architecture/CORE_CONTRACTS.md`, `docs/v2/first-region-baseline.md`.
> **상위 목적:** SGMG-01 — 깊고 다양한 세계관과 기승전결을 통해 플레이어가 세계관 최강자가 되는 경험.

## 1. 결론

- Node 수가 곧 몰입감은 아니다. **인과적 관계·지속성·기억·관찰 가능성**이 동반되어야 한다.
- **Entity, Location, Resource, Event, Knowledge** 5종과 방향성 Edge를 기반으로 기존 V2 데이터의 **읽기 전용 세계 그래프**를 우선 추출한다.
- 시간적 진실과 인물이 믿는 정보는 반드시 구분한다. 실제 사건의 유효 시점과 지식을 들은 시점도 구분한다.
- 처음부터 GraphDB·LLM Runtime·서버·Worker를 추가하지 않는다. 기존 `step(state,action,data)`, Condition/Effect, seed, Fact/Rumor, save 및 측정기를 우선 재사용한다.
- 현행 V2의 첫 지역(나루·성읍·교역·소문)을 인과 연쇄가 보이는 시범 지역으로 완성한 뒤, 다른 장르 세계로 확대한다.
- 목표 수량 1,000/10,000/100,000/1,000,000은 **기술적 용량·콘텐츠 생산 실험의 단계 가설**이며 게임 완결의 필수 임계값은 아니다.

## 3. 5종 Node의 범위 (구현 전 개념 모델)

| 유형 | 다루는 것 | 예시 ID | 필요한 핵심 관계 |
|---|---|---|---|
| **Entity** | 인간·괴물·신·인격체·조직·세력 | `ent_ferryman` | LIVES_AT, MEMBER_OF, KNOWS, OWNS, RIVALS |
| **Location** | 장소·마을·도시·국가·던전·차원 | `loc_ford` | CONNECTED_TO, PART_OF, PRODUCES, GOVERNED_BY |
| **Resource** | 식량·광물·마력·기술·상품·재고 | `res_flour` | PRODUCED_AT, CONSUMED_BY, TRADED_AT, OWNED_BY |
| **Event** | 출생·사망·교역·전쟁·혁명·발견 | `evt_convoy_arrival` | OCCURRED_AT, PARTICIPATED_IN, CAUSED_BY |
| **Knowledge** | 소문·비밀·사실·신앙·증언 | `kn_demand_report` | ABOUT, HEARD_FROM, BELIEVED_BY, CONTRADICTS |

**정의와 인스턴스 구별:** NPC 템플릿은 태어난 실제 NPC가 아니다. 사건 타입과 실제 발생 사건을 분리하고, 자원 종류와 개별 재고를 분리한다. V1과 V2의 동일 이름을 별도 ID로 식별하고 중복 합산하지 않는다.

### Edge 최소 제안

`{ id, fromId, type, toId, worldId, validFromMinute?, validToMinute?, sourceId?, canonStatus? }`

- 타입·ID 존재·단위·방향의 유효성을 검사한다.
- 동일 자산을 동시에 둘이 독점 소유하거나 죽은 인물이 사후 거래하는 모순을 금지한다.
- 인물의 말(믿음)과 세계의 Fact는 같은 Node로 자동 병합하지 않는다.
- 관측하지 않은 진실을 플레이어 UI로 누출하지 않는다.
- 저장 의미나 Core 계약을 바꾸지 않고 처음에는 **데이터 팩의 읽기 전용 추출·측정 결과**로만 구현한다.

## 4. 세계의 깊이를 만드는 인과 그래프

**예시: 마을에 밀가루 부족이 발생한 경우**

1. Resource: 방앗간 재고 감소.
2. Event: 상단의 공급 지연. `CAUSES` 재고 변화.
3. Entity: 상인은 오늘의 수요 정보를 보유하지만 뱃사공은 지난 상단의 정보만 보유.
4. Knowledge: `aboutDay`와 `heardDay`의 차이 때문에 불완전한 예측 발생.
5. Player: 정보 확인 → 짐표/운송/판매 여부 판단.
6. Event: 판매·운송에 따른 은화, 수요, 소문·관계 변화.
7. Entity: 다음 상단과 주민이 결과를 접하고 새 행동·대화가 열린다.

**중요:** 예시는 새로운 Canon이 아니라, 이미 존재하는 관계·경제·정보 경로를 더 깊이 잇기 위한 검증 시나리오다.

### 시간 인과의 불변식

- 사건에는 발생 게임 시간, 관련 행위자, 장소, 원인/결과를 기록한다(기존 필드 재사용).
- Knowledge에는 정보가 가리키는 시점과 습득 시점, 전달자를 구분할 수 있어야 한다(없을 땐 unknown).
- 먼저 일어난 사건을 나중 사건의 영향으로 거꾸로 수정하지 않는다. 과거 Fact는 유효기간을 종료하고 새로운 상태 사실을 이어받는다.
- 모순 검사 절차: **사전조건 → 사건 발생 → Effect → 유효기간 갱신 → 정보 전파 → 관찰자별 UI**.
- LLM이 설계 초안을 만들어도 실제 상태 전이는 V2 엔진의 결정론적 규칙으로 확정한다.

## 5. 생성 파이프라인: 양보다 개연성

1. **기존 세계 추출:** 현재 V2 팩의 Node 후보, 관계, 참조 및 시뮬레이션 채널을 스캔.
2. **역사·지리·자원 제약:** World Bible의 확정·보류 Canon과 현재 경제·시간 규칙을 조사.
3. **지역·조직 구체화:** 세력의 목표, 자원 흐름, 갈등, 지역 교통을 일관되게 연결.
4. **Entity 생성:** 직업, 역할, 위치, 관계, 목표, 알고 있는 정보와 출처를 부여.
5. **Event/Knowledge 생성:** 실제 사건 → 누가 목격·전달·오해했는지 → Storylet·대화·행동으로 구현.
6. **검증:** 형식·ID·참조·시간·인과·자원 수지·Canon·행동 가능성과 보상 연결.
7. **실제 플레이:** UI에서 정보/판단/행동/결과가 보이며 기존 세이브를 깨지 않는지 확인.
8. **Batch 확장:** 성공한 패턴은 재사용하되, 새 지역에는 고유한 원인과 관계를 부여한다.

**생성 도구 원칙:** 기존 validator와 `tests/v2/measure/content-graph.mjs` 등을 먼저 재사용. 스키마 도구나 외부 LLM API는 필요성·허용 비용·운영 계획을 확인한 후 선택적으로 도입.

## 6. 22개 장르의 상위세계관 연결 방식

**기본 필수 범위:** 사이버펑크, 아케인펑크, 아포칼립스, 판타지, 현대 판타지, 중세 판타지, 이세계, 회귀, 빙의, 환생, SF, 스페이스 오페라, 괴이·오컬트, 무협, 선협, 헌터, 게이트, 탑, 탑 등반, 미궁·던전, 배틀 아레나, 차원 유랑.

- **세계/문명/시대:** 사이버펑크·SF·스페이스 오페라·판타지·무협·선협 등은 지역/문명에 고유 문화·자원·기술·역사를 부여.
- **정체성·시간의 규칙:** 회귀·빙의·환생은 단순 장소가 아니라 정체성/기억/시간/사건 규칙으로 모델링.
- **이동·도전·생활 구조:** 게이트·탑·미궁·배틀 아레나·차원 유랑 등은 각각 다른 행동·위험·보상·이동 규칙을 제공.
- **연결 규칙:** `worldId`, 지역 간 이동, 자원과 세력, 세계의 경계와 파워 스케일을 명확히 관리.
- **완성 기준:** 장르 태그만 추가하지 않는다. 각 장르에는 플레이 가능한 고유 사건/행동, 결과, 다른 세계와의 관계, 테스트가 있어야 한다.

현 V2 계약의 세계 이동과 성장의 구체적 규칙은 Hard Gate 사항일 수 있으므로 문서 연구 단계에서 무단 확정하지 않는다.

## 7. 시뮬레이션 LOD — 전체 Node를 항상 '생각'시키지 않는다

| 단계 | 대상 | 처리 |
|---|---|---|
| L0 핵심 | 플레이어, 메인 NPC, 중요한 세력 | 상세 상태·행동·기억·사건; 필요한 경우에만 AI 추론 |
| L1 주변 | 마을 주민, 상인, 전투·거래 관련 NPC | 직업/목표/관계 기반 이벤트 처리 |
| L2 원거리 | 타 도시·국가·경제·인구 | 주기적 집계, 교역·전쟁·소문 이벤트 |
| L3 미관측 | 아직 방문하지 않은 장소와 존재 | seed와 Canon 제약에 따른 필요 시 구체화 |

**지속성:** 이전에 관측된 이름·사건·사망·관계는 다시 방문해도 임의로 바뀌면 안 된다. 멀리 있는 인물의 개인 행동 대신 중요한 집단적 변화만 저장할 수 있다.

## 8. Node 생성 비용 산정: 측정 우선

`검증된 Node당 비용 = (입력 토큰 비용 + 출력 토큰 비용 + 재시도/수정 비용 + 검사 비용) / 검증 통과 Node 수`

- Node 타입마다 샘플 100~1,000개를 생성해 토큰·모델·재시도 횟수·유효율·평균 Edge·검증 비용을 기록.
- 게임 플레이 중 API 운영비는 **별도** 산출.
- 동일한 이름/직업만 바꾼 Node는 유효 콘텐츠로 계산하지 않는다.
- **가상의 계산 예시:** 입력 3,000토큰, 출력 1,200토큰, 가정 단가 $2/$10 per 1M이면 1차 생성비 $0.018/후보. 검사·재시도 3배를 가정하면 $100당 약 1,851개 **후보**를 생성 가능. 유효율이 60%이면 약 1,111개. 실제 모델 가격/청구액이 아니다.
- 목표 1만/10만/100만 Node는 실측 비용과 콘텐츠 밀도가 입증되기 전에는 생산 승인량이 아니다.

## 9. 실현 가능한 MG 후보 (순차적, 자동 확정 아님)

| 단계 | 직접 산출물 | 검증 |
|---|---|---|
| **WNG-0** | 최신 V1·V2 분리 Node 인벤토리(중복 제거·출처·관계 수) | 실제 ID/참조를 기반으로 재현 가능한 유형별 집계 |
| **WNG-1** | 첫 지역의 read-only World Graph 투영 | Node/Edge 추출이 기존 런타임에 영향 없음 |
| **WNG-2** | 밀가루·상단·나루·상인의 인과적 플레이 시나리오 | 정보 → 선택 → 타 Node의 관찰 가능한 변화 |
| **WNG-3** | 타입별 콘텐츠 후보 생성과 형식·의미 검증 | seed 재현, 유효 ID/타입/시간/Canon |
| **WNG-4** | 100/1,000 Node 소규모 생성·실측 | 유효율, 고립률, 관계 수, 저장 크기, 생성 비용 |
| **WNG-5** | 2~3지역으로 확대, 고유 역사/자원/갈등 연결 | 지역별 고유 활동·선택·사건·결과 |
| **WNG-6** | 상위세계관 22장르와 세계 이동 정합성 조사 | 기존 성장/CANON 계약 충돌과 별도 승인 필요 사항 식별 |

### 평가 지표 (수치 임계값은 별도 사전 확정)

1. **유효 Node 비율** — 형식·참조·시간·Canon·행동 검사 통과율
2. **고립 Node 비율** — 실제 게임 상호작용으로 이어지는 Edge가 없는 비율
3. **인과 전파율** — 한 Node의 변화가 다른 Node의 상태·선택을 바꾼 비율
4. **정보 출처 추적률** — 목격·전달·오해·대체 경로 복원 가능 비율
5. **콘텐츠 다양성** — 반복 템플릿/동일 행동, 지역 고유 관계·사건
6. **장기 일관성** — 장시간 step, 사망·후계, save/load 후 모순·누락 건수
7. **성능과 비용** — 활성 Node 수, step 지연, 저장 크기, $/유효 Node

**규칙:** 기존 MG-039·Road News 측정 기준을 근거 없이 완화하지 않는다. 수치가 없는 새로운 기준은 먼저 측정하고 정한다.

## 10. 구현 우선순위·금지사항

- 최우선: 기존 V2의 실제 Node 수/연결도를 **읽기 전용으로 측정**하고 첫 지역의 인과적 연결을 늘리는 것.
- 다음: 플레이어에게 정보와 결과가 드러나는 지역 서사 밀도를 높이는 것.
- 이후: 검증된 생성 템플릿과 비용 측정으로 Node 수를 확장하는 것.
- 금지: 노드 수만으로 게임 완성 선언; 기존 Fact/Rumor를 단일 진실로 뭉개기; 모든 NPC에 LLM 상시 호출; 미확정 Canon 변경; 기존 Save/Core/결정론 계약 파괴; V1 수정; 불필요한 GraphDB/API 의존성 도입.
- 코드·저장 구조·세계관 핵심 Canon에 Hard Gate가 생기면 현재 `DEVELOPMENT_RULES.md`에 따른다.
