## 2. Exa 추가조사 — 원보고서의 결론을 강화하거나 수정하는 증거

### A. 핵심 동사는 맞지만 '즉시 정답 판정'은 위험하다

**[The Case of the Golden Idol 설계자 인터뷰, Game Developer (2022-11-01)](https://www.gamedeveloper.com/design/case-of-the-golden-idol)**: 제한된 단어로 완성하는 문장은 자유 텍스트 파서의 좌절과 객관식의 가짜 추리 사이를 피한다. 그러나 모든 슬롯을 즉시 알려 주면 무차별 대입이 발생하고, 전체 오답만 알려 주면 어디서 진전했는지 알 수 없다. 제작진은 중간 피드백을 도입했지만 난이도·분량이 줄어드는 대가를 인정했다.

**[Golden Idol 실제 테스트 인터뷰, Game Developer (2023-03-02)](https://www.gamedeveloper.com/business/-the-case-of-the-golden-idol-i-used-frequent-testing-to-improve-its-mystery-solving)**: 개발자가 정답을 알고 테스트하는 것은 한계가 있으므로 4~5명의 플레이를 관찰했다. 'Thought Path'(단서 → 중간 결론 → 후속 단서)를 설계하고 너무 이른 정답/지루한 우회를 고쳤다. 숫자만 보지 않고 사고 경로와 발언을 관찰했다.

**[The Roottrees are Dead 개발자 인터뷰 (2025-07-31)](https://zencastr.com/z/OIcW69cP)**: 제작진은 완성할 구조(가계도·논리 관계)를 먼저 정하고 퍼즐에 필요한 증거와 접근 경로를 역으로 설계했다. Steam판의 수첩·힌트 인터페이스 개선 사례는 '퍼즐 자체'와 '정보를 조작하는 UI'를 별개의 작업으로 관리해야 함을 보여 준다.

**결정:** J3 RC에는 1장의 **짧은 인과 명제 하나를 푸는 수동형 짐작 장부**를 우선 구현한다. 단서가 충분한 시점에 근거를 제시하며 결론을 검증한다. '두세 칸 채우기'는 표현 방식일 뿐 확정 사양이 아니다. **2~3개 슬롯 묶음이라도 후보가 극히 적으면 금세 브루트포스로 풀리므로**, 오답을 틀린 칸별로 알려 주지 않고, 근거 없는 즉시 재검증을 허용하지 않는다. 검증 난도는 실제 후보 수와 단서 흐름으로 먼저 측정한다.

### B. '추측'과 '세계의 진실'을 분리해야 한다 — 기존 보고서의 중요한 보정

저장소 실제 `web/v2/data/world.js`는 `fact_ruins_secret.initial = "unknown"`이고, `act_investigate_ruins` 성공 시 `fact_ruins_secret = "bandit_hideout"`를 기록한다. `fact_spring_cause` 및 `fact_spring_fouler`도 해당 관찰/행동에서 설정된다. 따라서 **'팩에 사실 키가 있다' = '플레이 시작부터 완전히 확정된 검증 가능한 객관적 정답이 state에 있다'는 아니다.** 데이터의 규정된 결과와 현재 세계에 기록된 참값을 구별해야 한다.

**[Heaven's Vault 제작진 인터뷰 (2020-01-24)](https://www.gamedeveloper.com/business/road-to-the-igf-inkle-s-i-heaven-s-vault-i-)**: 즉시 번역 정답을 보이지 않는 이유는 무작정 입력하는 플레이를 막고 근거를 읽게 하려는 것이다. 오해나 불확실성도 서사에 의미를 부여한다. TxtRPG가 정답을 아는 세계라는 점과 달리, **검증이 가능한 때에만 검증해야 한다**는 설계 규율은 적용된다.

**[Return of the Obra Dinn 제작자 개발 기록 (2014-11)](https://dukope.com/devlogs/obra-dinn/tig-06/)**: 개별 운명을 바로 확인하는 피드백과 브루트포스의 유혹 사이에서 고민한 기록이다.

**결정:** RC에서 가설은 `proposed`(주장), `supported`(단서에 의해 지지), `confirmed`(실제 조사·증인·행동으로 확인), `disproved`(반증)로 **표현 레벨**을 구분한다. 모든 네 레벨을 필수 새 저장 상태로 구현하라는 뜻이 아니다. 사실이 아직 `unknown`이면 판정기에 숨은 정답을 만들어 넣지 않고 `확인할 근거가 부족하다`고 안내한다. 세계관의 미결 질문(C-03 등)은 퍼즐 정답으로 만들지 않는다. 초기 RC에서는 원칙적으로 **오답에 시간·신뢰 페널티를 부과하지 않는다**. 이런 비용은 추리 학습을 위축시키고 기존 정책 측정을 변형할 수 있으므로 J3 관찰 이후 별도 실험으로 판단한다.

구현자는 반드시 플레이 직전 상태에서 실제로 답이 판정 가능한 문제인지, 복수 단서로 접근하는 길이 있는지, '장부 확인만으로 금지된 사실이 노출되지 않는지'를 fixture로 먼저 증명한다. 없다면 데이터를 새로 정본화하지 말고, **이미 확정된 사건/결과로 확인 가능한 가설 하나**를 선택하거나 J3 RC의 장부를 '가설→현장 확인' 과정으로 구현한다.

### C. '위험 시계'는 숫자 UI가 아니라 믿음 UI다

**[Blades in the Dark 공식 규칙: Progress Clocks](https://bladesinthedark.com/progress-clocks)**: 시계는 방법이 아니라 장애물·다가오는 결과를 표현한다. 시계의 칸은 진행을 이해하도록 돕는 추상화이며 그것이 세계 진행을 결정하는 주체가 아니다.

**결정:** `state`의 실제 무리 크기·건넘 시각·다음 RNG 값에서 시계 눈금을 생성하지 않는다. **오직 현재 인물의 `knowledge`·관측 `aboutDay`·`firstSeenDay/lastSeenDay`·출처·명시적으로 알 수 있는 현재 시각**만으로 '소식 없음 / 오래된 보고 / 최근 관측 / 확인된 건넘' 등 **서술형 구간**을 보여 준다. 정보가 불충분하면 빈 시계/미상으로 보이고 정밀한 남은 일수·숨은 임계치·9일 주기를 역산한 정답을 표출하지 않는다.

**비간섭 테스트:** 실제 참값·미공개 사건만 다른 `state A,B`에 대해 인물에게 공개된 앎이 같으면 표시 결과가 완전히 같아야 한다. 시계는 읽기 전용이며 RNG와 Save를 바꾸지 않는다.

### D. J3 검증은 사람이 직접 체험하는 RITE형 반복 테스트다

**[Golden Idol 개발 인터뷰 (2023)](https://www.gamedeveloper.com/business/-the-case-of-the-golden-idol-i-used-frequent-testing-to-improve-its-mystery-solving)**: 제작자가 이미 아는 답을 스스로 테스트해서 얻는 품질 신호에는 한계가 있다.

**[Microsoft Game Studios: RITE 방법론, Age of Empires II 사례](https://www.jpattonassociates.com/wp-content/uploads/2015/04/rite_method.pdf)**: 사용자가 어디서 실패하는지 관찰하고 원인이 명확한 UI 문제를 수정한 다음 **다음 사용자로 변경 효과를 다시 검증**한다. 보편적인 표본 수를 보장하는 방식은 아니다.

**[게임 사용자 조사자 Steve Bromley: 첫 15분 테스트](https://www.stevebromley.com/blog/2010/09/01/the-thirty-minute-facebook-game-usability-test/)**: 처음 접하는 대상이 지시 없이 무엇을 해야 하는지 이해하는지를 관찰하고, 개입 없이 질문·망설임·진행 중단 지점을 기록하는 방법.

**결정:** (1) 소유자 J3 1회 완주와 (2) 가능하면 이 세계를 모르는 목표 플레이어 3~5명의 15~25분 블라인드 초반 테스트를 분리한다. 3~5명은 실무적 출발점이지 성과의 통계적 보장은 아니다. 자동 검증으로 J3 통과를 선언하지 않는다.

## 3. 확정한 재플레이 빌드

### A. 기준선 — 현행 상태

`feature/v2-core@b12594f877f61af932866dd9f051322f16261e45`: **비교 기준(컨트롤)**로 동결한다. 필요하면 이 빌드에서 초반 10~15분만 재확인하여 오리엔테이션과 단서 획득 경로를 비교한다. 이미 보고된 J3 불합격의 직접 원인('새 정보를 얻었을 때의 쾌감 부재')을 해결하지 못했으므로 **주 재플레이 대상으로 선택하지 않는다**.

### B. 시험 빌드 — J3 RC1 (선택)

현행 기준선 위에 기능을 **두 개만** 넣은 커밋을 검증 후 태그 `j3-inference-clock-rc1`로 고정한다(태그 이름은 예약 제안, 현재 존재하지 않음).

1. **가설/짐작 장부, 첫 지역 1개의 완전한 단서 경로.** 중간 결과는 `의심/근거/현장 확인`으로 구별. 서로 다른 정보를 가진 상태에서 후보가 달라지고, 인물은 보지 못한 정보를 알지 못한다. 고른 가설이 실제 조사·대화·플래그의 선택에 영향을 주도록 구성하되, 진실을 미리 말하지 않는다.
2. **아는 만큼 보이는 시계.** 무리의 실제 숨은 상태와 독립적으로 정보의 최신도·신빙성과 다가오는 위험을 이해할 수 있도록 한다. 미상 표기 필수.
3. 장부의 '세계가 기록한 이름', Node 증식, 시간 그래프, NPC 자율, J1·J2 수치 밸런스 재설계는 **넣지 않는다**. 사용자 평가에서 바뀐 경험의 원인을 식별하기 위해서다.

**RC1 생성 조건:** 엔진 `step` 계약·State/Save schema·굴림 커서 불변. 패리티(기존 행위를 선택한 경력의 바이트 일치), 알려진 기존 성능 기준 유지. 기존 저장→새 저장→복원, 390px, 키보드/스크린 리더, 실제 Chromium, V1/V2 full 검증. 가설이 검증 불가능하거나 누출이 발생하면 RC1을 출하하지 않고 수정 후 다시 검증한다. 기능 구현과 통합이 끝난 **정확한 SHA**를 태그/릴리스 노트에 적는다.

**예외:** 장부의 실질적인 판단·검증 동사가 위 조건에서 구현 불가능하다면, 가짜 정답 UI로 대체하지 않는다. 그때는 RC 태그를 만들지 않고 명시적 최소 Core 변경 설계·회귀 측정을 선행한다. 그래도 J3 본 시험 대상은 기능 없는 현행 빌드가 아니라 **검증 가능한 판단 동사가 들어간 최초 후보**를 원칙으로 한다.

## 4. J3 실전 관찰표 (RC1 고정 후)

재플레이 때는 개발자가 정답이나 다음 경로를 미리 설명하지 않는다.

| 평가 장면 | 기록할 것 | 실패 신호 |
| --- | --- | --- |
| 시작 3~5분 | 플레이어가 자기 말로 지금의 목표와 첫 행동을 설명하는가 | 첫 행동을 몰라 멈춤 |
| 첫 소문 획득 | 소문을 읽고 '어떤 질문을 해결하고 싶은지' 말하는가 | 텍스트를 건너뛰고 버튼만 누름 |
| 첫 가설 제출 | 어떤 단서를 결합했으며 왜 그런 답을 골랐는가 | 답을 알 수 없거나 무작위 클릭 |
| 반증/확인 | 성공·실패의 근거와 다음 할 일이 납득되는가 | 정답을 외부에서 주입한 느낌 |
| 위험 시계 등장 | 출처와 정보 나이를 이해하며 행동을 변경하는가 | 참값으로 착각, 지나친 확신 |
| 결전·정점 | J1 위험, J2 정보 지연, 마지막 만족감 | 버튼 수와 무관하게 비어 있는 승리 |

제안 보조 지표(합격 자동화 기준 **아님**): 첫 가설까지의 유효 행동 수, 첫 근거 확인까지의 시도 수, 플레이어가 설명할 수 있는 단서 수, 연속된 무목표 클릭 수, 주관적 만족도(자유 서술). 소유자 J3 판정은 별도 기록한다.

## 5. 재플레이 이후의 결정 트리

**J3 불합격 — 발견 동사가 작동하지 않을 경우:** 새 Node를 늘리지 않는다. 관찰 로그를 기준으로 '단서 부족/가설 피드백 부실/다음 행동 불명/읽기 피로'로 분류하고 P0를 수정한 **RC2**를 재시험한다. 근거 없는 추가 기능을 얹지 않는다. UI 문제는 RITE처럼 수정 후 독립 확인한다.

**J3 통과(초반)지만 결전·정점 불만족:** 핵심 추리 동사는 보존한다. J1(b)/J2(b)만 분리 실험하며 기존 `m8-balance-preregistration.md`의 목표를 사후에 바꾸지 않는다. 새로운 변화는 새 사전 등록과 별도 표본으로 측정한다.

**J3 전체 통과:** RC1의 정확한 커밋을 결정적 1.0 후보 기준선으로 고정한 다음, J4 출시/메인 통합은 `decision-packet-2.md`가 정한 별도 실행 결정에 따라 진행한다. 이후 순서:
- **P1**: '세계가 기록한 이름' 수첩 통합(기존 정보의 재배치, 중복 제거; 수첩을 삭제하기보다 회귀와 접근성 검증).
- **P2**: `#405` 문서를 최신 J3 상태로 업데이트하고 읽기 전용 Temporal Graph의 **1개 세로 절편** 구현. 시간·증거 출처·관찰자 범위, Save 및 Node/Chromium 동등성.
- **P3**: 제한된 NPC 자율 행동(N4)과 부관의 목소리(N3), 장기 인과 실험. 기준선 대비 차이를 계측.
- **P4**: `#358` 카탈로그는 1.0과 분리 보관하고, 실제 플레이로 이어지는 인과 '전선'의 틀만 기존 지역에 먼저 적용. 새 Node는 **플레이어가 경험 가능한 상호작용을 증가시킨 경우**에만 유효 증가로 센다.
- **P5**: 차후 추가 세계/장르 및 대규모 생성은 위 수직 절편과 자동 정합성 검사 통과 후 단계적 도입.

## 6. 범위, 권한, 검증 상태

- 이 문서는 연구 및 **개발 우선순위 결정**이다. 실제 J3 RC1 빌드 구현·태그·브라우저 테스트·소유자 플레이테스트를 했다는 뜻이 아니다.
- 현재 PR #354는 반영돼 Hard Gate는 제거되었지만, 공개 배포와 `main` 병합, 정본의 미결 사항, 외부 비용은 다른 정책/실제 권한의 제약을 받는다.
- J3의 목표는 '완성 판정'을 자동 점수로 대체하는 것이 아니라, **정보를 플레이어가 판단으로 전환한 순간이 실제로 생겼는지** 확인하는 데 있다.
- 원보고서의 상세 시장 수치·인기도·매출 모두를 새로 검산하지는 않았다. 이 부록의 추가 조사는 구체적인 **게임 디자인, 지식 상태, 재플레이 판정의 3개 영역**에 집중한다.
